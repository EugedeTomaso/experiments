# Hetzner CX23 Development Deploy Design

## Problem

We need a cheap first deployment of the current app on Hetzner Cloud to measure real-world performance before spending more on infrastructure. The app is a single-stack Docker Compose deployment with PostgreSQL, Django, a Node-based collaboration service, and Nginx serving the frontend.

The existing provisioning script already creates a Hetzner Cloud server and bootstraps the stack, but it still assumes an older server type, uses an SSH-based Git clone flow, and is biased toward a more expensive default shape than we want for this test.

## Goal

Create a disposable, low-cost Hetzner deployment for the remote `development` branch using a single `cx23` server, public IP access over HTTP, and autogenerated internal secrets.

## Constraints

- Use the Hetzner Cloud project tied to the provided API token.
- Keep monthly cost minimal for this first performance test.
- Do not require a domain, HTTPS, backups, or persistent extra storage yet.
- Treat the environment as temporary and easy to destroy/recreate.
- Keep the deployment reproducible through the repo's provisioning automation.

## Chosen Approach

### Infrastructure Shape

- One Hetzner Cloud server.
- Server type: `cx23`.
- Location: `nbg1`.
- Firewall: allow `22`, `80`, and `443` only. `443` remains unused for now but can stay open without changing the current test scope.
- No load balancer.
- No managed database.
- No backups.
- No attached volume.

### Application Topology

The existing `docker-compose.prod.yml` remains the runtime topology:

- `db`: PostgreSQL 16
- `backend`: Django + Gunicorn
- `collab`: Node websocket service
- `nginx`: static frontend + reverse proxy for API and websocket traffic

Everything runs on the same VM. This is intentionally simple so the first measurement reflects the actual stack with minimal infrastructure noise.

### Deployment Inputs

- Deploy target: remote branch `development`
- Public entrypoint: `http://<server-ip>`
- Frontend build-time config:
  - `VITE_API_BASE=http://<server-ip>`
  - `VITE_COLLAB_URL=ws://<server-ip>/ws`
- Django runtime config:
  - `DJANGO_ALLOWED_HOSTS=<server-ip>`
  - `CSRF_TRUSTED_ORIGINS=http://<server-ip>`

### Secret Management

The provisioning script generates all internal secrets during bootstrap:

- `DJANGO_SECRET_KEY`
- `ENCRYPTION_KEY`
- `DB_PASSWORD`
- `INTERNAL_API_KEY`
- `JWT_SECRET`

This keeps the deploy self-contained and avoids asking the user for values that are safer to generate locally at provisioning time.

### Provisioning Flow

1. Validate the Hetzner Cloud token by making authenticated API calls.
2. Create or reuse the project-scoped firewall.
3. Create the `cx23` server in `nbg1`.
4. Bootstrap the server with cloud-init.
5. Clone the repo onto the new server.
6. Check out the remote `development` branch explicitly.
7. Generate the production `.env` file using the public server IP and generated secrets.
8. Build and start the stack with Docker Compose.

### Git Access Strategy

For this disposable test, the simplest clone path is preferred:

- If the repository can be cloned anonymously over HTTPS, use that.
- Avoid SSH deploy-key setup unless strictly necessary.

This removes an avoidable provisioning dependency and makes repeated create/destroy cycles faster.

### Verification Plan

After bootstrap completes, verify:

- `cloud-init` finished without fatal errors
- Docker services are up
- frontend responds on `/`
- API responds through Nginx
- websocket endpoint `/ws/` is reachable

This is a smoke test only. Performance profiling comes after the stack is live.

### Rollback Plan

The environment is disposable by design.

- If bootstrap fails, destroy the VM and recreate it from scratch.
- If `cx23` performs poorly, destroy it and rerun the same flow on a larger server type.
- Do not treat this first VM as stateful or production-safe.
